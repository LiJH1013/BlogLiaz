一个聊天模型可以解释报错，也可以帮忙拟一份 Issue，但它不会因为说出“我已经创建任务”就真的改动了项目。模型生成的是 token，创建 Issue 需要调用外部接口。在两者之间，还隔着参数校验、身份认证、权限判断、失败重试和操作记录。

不妨把目标定得具体一点：做一个研发知识助手。有人报告“文章筛选后刷新页面会丢失条件”，助手要查询项目文档、搜索相关代码、核对历史 Issue，给出原因和修改建议。确认判断无误后，它可以生成任务草稿；只有用户批准，系统才把草稿提交到项目管理平台。

这个过程里有三种容易混在一起的能力。大模型从训练中获得参数知识，能理解 URL、前端状态和 Issue 的含义；RAG 把当前项目的文档临时放进上下文，让回答有本地证据；工具则读取代码或调用外部 API，取得新信息，也可能改变外部状态。模型负责理解和选择，运行时负责执行与约束。

沿着这条分界线往回看，Agent 的结构会清楚很多：注意力机制让模型利用上下文，大规模预训练让模型形成通用语言能力，RAG 接入可更新的知识，工具调用让输出变成行动请求，运行时再用状态和控制循环把多步行动组织起来。Agent 不是一种位于 Transformer 之后的新模型，它是一套围绕模型搭出的软件系统。

## 注意力在上下文里寻找关系

模型收到的句子会先被切成 token。token 可能是一个汉字、词的一部分、标点或代码片段，具体边界由分词器决定。每个 token 随后被表示成一组数字，也就是向量。向量本身没有“这是筛选条件”的可读标签，含义来自训练中学到的表示，以及它和周围 token 的关系。

考虑一句简单的需求：“刷新后保留文章筛选条件。”模型理解“保留”的对象时，需要把它与前面的“文章筛选条件”联系起来；看到“刷新”时，又要想到页面状态重新初始化。句子变长以后，一个 token 应该参考哪些位置，不能只按固定距离决定。注意力机制为当前 token 计算一组权重，让相关位置对新表示贡献更多信息。

Transformer 使用的缩放点积注意力可以写成：

```text
Attention(Q, K, V) = softmax(QKᵀ / √dₖ)V
```

Q、K、V 都由输入向量经过不同的线性变换得到。可以把 Query 理解成当前位置正在寻找什么，Key 表示各位置能够用什么特征被匹配，Value 则是匹配后真正取回的内容。这个说法只帮助理解计算分工，它们在模型里仍然是向量，不是自然语言写成的问题、索引和答案。

`QKᵀ` 计算 Query 与所有 Key 的匹配程度。数值越大，当前位置越倾向参考那个 token。向量维度变大时，点积的绝对值也容易变大，除以 `√dₖ` 可以让后续 softmax 的输入保持在较合适的范围，避免权重过早挤到接近 0 或 1。softmax 再把分数变成总和为 1 的权重，最后用这些权重对 V 做加权求和。

这一步并不是从句子里挑出一个词复制过来。每个位置会同时吸收多个位置的信息，只是贡献不同。经过多层变换后，“筛选条件”的表示可以带上“刷新后仍需存在”这层关系，后续网络再利用这些表示预测输出。

多头注意力会并行执行多组 Q、K、V 投影。不同头没有人工规定的语法职责，但多组投影给了模型从不同表示子空间捕捉关系的机会。有的关系靠近词法，有的跨越较远位置，有的与代码符号或指代相关。各个头的结果拼接并再次投影，成为下一层的输入。

注意力本身不包含顺序。把相同 token 打乱，如果没有额外位置信息，计算无法仅凭集合判断谁在前谁在后。Transformer 因此需要位置编码或位置表示。生成模型还会使用因果遮罩，使当前位置只能看到已经出现的 token，不能偷看尚未生成的答案。模型每次预测下一个 token，再把新 token 接回序列继续计算。

注意力有一个很重要的边界：它只处理已经进入上下文的信息。项目文档没有放进输入，注意力就无从“关注”那份文档；训练截止后新增的 API，也不会因为注意力算得更准而自动出现。把注意力称作模型内部的信息路由更合适，它不是数据库检索，更不是联网搜索。

[《Attention Is All You Need》](https://arxiv.org/abs/1706.03762)在 2017 年提出以注意力为核心的 Transformer 架构。今天的大语言模型在规模、训练数据、位置表示和网络细节上已经有大量变化，但从上下文中计算 token 关系，仍然是理解后续能力的起点。

## 大语言模型仍在预测下一个 token

语言模型的基础训练目标可以压缩成一句话：给定前面的 token，预测下一个 token 的概率分布。训练文本中已经知道正确的后续 token，模型根据预测误差调整参数。大量样本反复训练后，参数会编码语言结构、常见事实、代码模式和问题之间的关联。

“预测下一个 token”听起来比问答和写代码简单得多，但训练样本里本来就包含说明、推导、对话、程序和文档。要在各种上下文中持续预测准确，模型必须利用上下文关系，形成能够复用的内部表示。推理时给出问题，回答可以看作符合当前上下文的一段后续序列。

预训练模型学会了续写，却不一定会稳定遵循用户指令。指令微调会加入任务与回答形式更明确的数据，让模型熟悉问答、摘要、工具参数等交互方式。偏好优化再利用人类或其他反馈信号，调整模型对不同回答的取舍。这里改变的是模型行为分布，不会替系统增加数据库权限，也不会凭空接上一套项目文档。

研发知识助手询问“这个项目把筛选状态放在哪里”时，模型可能根据常见前端实践回答 `localStorage`、React state 或 URL 查询参数。这些猜测都说得通，却只有代码和项目文档能确定当前实现。参数知识适合解释一般概念，不能充当项目事实。

上下文窗口允许程序把更多资料与问题一起交给模型，但窗口大不等于可以把仓库、历史对话和所有工具输出全部塞进去。无关内容会占用计算和费用，也会干扰模型找到当前步骤需要的信息。长任务还会不断累积搜索结果、错误日志和中间判断。系统需要决定保留原文、生成摘要、写入结构化状态，还是暂时丢弃。

模型也可能生成与上下文不一致的内容。它的目标是产生高概率的后续 token，并没有一个独立事实数据库在每句话后面盖章。要求模型“绝对不要编造”只能影响行为倾向，不能把概率生成变成确定性查询。需要准确来源时，系统要提供来源；需要确认操作结果时，系统要读取工具返回值。

工具调用也遵循同样的生成机制。模型并没有伸手碰到外部程序，它只是生成一段满足工具 schema 的结构化请求。比如：

```json
{
  "name": "search_code",
  "arguments": {
    "query": "searchParams category tag query",
    "path": "app/articles"
  }
}
```

程序解析这段请求，检查参数并执行搜索，再把结果放回下一轮模型输入。模型可以提出调用意图，执行成功与否只能由运行时和工具结果确认。这个区别也是 Agent 安全边界的开端。

## RAG 把外部资料带进当前上下文

项目知识会变，模型参数不会跟着每次提交自动更新。重新训练模型的成本高，也很难为每条回答提供清晰来源。RAG，也就是检索增强生成，在生成前从外部知识库取回相关材料，再把材料与问题一起交给模型。

一套常见的离线索引和在线查询流程大致如下：

```text
原始文档 → 清洗与切分 → 向量化 → 建立索引

用户问题 → 查询处理 → 召回 → 重排 → 拼接上下文 → 模型回答
```

索引阶段先把 Markdown、网页或其他资料清洗成适合检索的文本，再切成若干片段。每个片段通过 embedding 模型变成向量，与来源地址、标题、版本和权限标签一起写入索引。查询时，同一类 embedding 模型把问题也变成向量，系统寻找距离较近的文档片段。

embedding 描述的是语义位置，不直接生成答案。两个表述不同的问题可能有相近向量，比如“刷新后筛选丢了”和“如何让过滤条件持久化”；“状态”一词在前端、数据库和流程状态机里却可能指向完全不同的内容。向量检索擅长语义近似，精确符号、错误码、函数名通常更适合关键词检索。工程中经常把两类结果合并，再用重排器或规则确定最终顺序。

用户的问题也不一定适合直接拿去检索。“为什么这个功能又坏了”依赖前文才能知道“这个功能”指文章筛选，检索层要从会话和任务状态中补齐对象。复杂问题还可以拆成几条查询：一条找产品约束，一条找当前实现，一条找相关历史决策。查询改写的输出应该保留原问题，不能让模型改写后悄悄换掉用户意图。研发助手若把“刷新后丢失筛选”改成“如何用 localStorage 保存状态”，就已经提前押注了实现方案，URL、服务端状态等证据可能因此召回不到。

检索结果进入生成上下文时，还要带上来源之间的关系。某段设计文档提出目标，另一段维护记录说明目标已经修改，两段文字分别看都相关，版本顺序却决定应该采用哪一个。拼接器可以按文档、时间和标题组织片段，并明确标出每段来源，避免把互相冲突的句子连成一份看似一致的材料。模型遇到冲突时应展示差异或继续查询，不要自行编出一个折中版本。

切分会直接影响召回。片段太大，一个向量需要概括许多主题，具体问题的信号容易被稀释；片段太小，函数说明与限制条件可能被拆开，取回其中一半仍然无法回答。文档标题、代码边界和段落结构通常比固定字符数更有参考价值。相邻片段可以适当重叠，但重叠过多会让上下文出现大量复读。

权限也应进入检索链路。研发助手收到用户身份后，只能在该用户可访问的项目和文档中召回内容。先全库检索再让模型“忽略无权内容”已经造成数据暴露。权限过滤要发生在资料进入模型上下文之前，检索日志同样不能泄露无权文档的标题和摘要。

召回之后通常还要重排。第一阶段用较低成本取回几十个候选，第二阶段结合完整问题判断哪些片段更能支持答案，最后只把有限数量的证据交给模型。每个片段应保留稳定来源标识，回答中的引用才能回到具体文档，而不是只写一句“根据知识库”。

RAG 失败可以沿数据流定位。没有召回正确片段，要检查索引、查询改写和过滤条件；正确片段在候选里但没进入上下文，问题多半在重排或数量限制；相关段落被切断，要调整切分；证据已经完整进入上下文而回答仍然错误，才轮到生成提示、模型能力和输出校验。

把所有错误都归因于模型，会让团队不停改提示词，却放过已经失效的索引。反过来，召回指标很高也不能证明最终回答正确。RAG 至少有检索与生成两段质量，端到端任务还要检查引用是否真的支持结论。

[RAG 原始论文](https://arxiv.org/abs/2005.11401)把参数化生成模型与外部非参数记忆结合起来，重点之一就是知识更新和来源问题。今天工程里的 RAG 已经扩展出混合检索、重排、权限过滤等大量做法，基本边界没有改变：它把资料提供给模型，不替模型完成外部操作。

回到研发知识助手，RAG 可以检索维护文档、架构说明和编码规范。实时搜索代码则更适合作为工具，因为代码不断变化，用户问题还可能需要精确匹配符号。两者可以共存，不需要把所有信息源都强行做成向量库。

## 工具调用把意图交给程序执行

一个工具需要说清楚名称、用途、输入、输出、错误和副作用。模型根据名称与描述选择工具，运行时根据 schema 判断参数是否合法，业务层再决定当前用户有没有调用资格。函数已经存在，不代表它就适合直接暴露给模型。

下面是创建任务草稿的简化契约：

```json
{
  "name": "prepare_issue_draft",
  "description": "根据已经核验的证据生成 Issue 草稿，不提交到远端",
  "input_schema": {
    "type": "object",
    "properties": {
      "title": { "type": "string", "maxLength": 120 },
      "body": { "type": "string" },
      "evidence_ids": {
        "type": "array",
        "items": { "type": "string" },
        "minItems": 1
      }
    },
    "required": ["title", "body", "evidence_ids"],
    "additionalProperties": false
  }
}
```

这里刻意把“生成草稿”和“提交 Issue”拆成两个工具。前者只改变任务内部状态，后者会影响外部项目。用户可以查看并修改草稿，提交工具则要求明确批准。拆分之后，审批对象、审计日志和失败恢复都有具体边界。

一次工具调用会经过这些步骤：

```text
模型提出调用 → 解析并校验参数 → 检查身份与权限
→ 执行工具 → 规范化结果 → 写入状态 → 返回模型
```

schema 校验只能证明 `title` 是字符串，不能证明标题适合当前项目。业务校验还要检查目标仓库、证据归属和用户权限。对于提交、发送、删除、付款这类操作，系统需要独立策略，不能把“请谨慎调用”写进提示词就算完成权限控制。

读取型工具也不是天然安全。文件读取要限制允许目录，搜索接口要套用访问控制，网页抓取要防止请求内网地址。工具输出可能包含恶意页面中的提示词注入，不能因为文字来自“工具”就把它当系统指令。来源标签和信任级别应该跟结果一起保存。

工具描述过于宽泛时，模型很难选对。`manage_project` 同时负责搜索、创建、修改和关闭任务，参数会迅速膨胀，权限也难以细分。工具拆得过碎同样麻烦，模型要在几十个近似名字中选择，还要进行多次没有业务意义的往返。边界通常跟业务动作和副作用一致：搜索代码、读取文档、准备草稿、提交任务分别承担清楚的责任。

工具返回值要让程序和模型都能判断结果。只返回一段“操作失败”无法支持重试决策，推荐至少包含状态、数据、错误类型和是否可重试：

```json
{
  "ok": false,
  "error": {
    "type": "rate_limited",
    "message": "远端接口限制请求频率",
    "retryable": true,
    "retry_after_seconds": 30
  }
}
```

空结果也不是成功答案。搜索确实执行完成但没有命中，可以返回 `ok: true` 与空数组，同时附上查询范围。模型随后决定改写查询、换工具或向用户补问。超时、权限拒绝和参数错误的处理方式不同，运行时不能把它们压成同一个字符串。

## Agent 是一个受约束的执行循环

当模型能够读取工具结果，并根据新信息决定下一步，多轮执行循环就出现了。[ReAct 论文](https://arxiv.org/abs/2210.03629)研究了推理与行动交错的方式：行动让模型从外部环境取得信息，观察结果再影响后续推理。工程实现不必复刻论文提示格式，但观察、选择行动、接收结果和调整计划这条链路很有用。

最小循环可以写成：

```text
接收目标
  → 读取任务状态并组装本轮上下文
  → 模型选择回答、调用工具或请求人工输入
  → 运行时检查并执行允许的动作
  → 记录观察结果并更新状态
  → 判断继续、完成、失败或暂停
```

目标描述任务完成条件。研发助手的目标不是“研究筛选问题”，而是“基于可引用的项目证据给出原因与建议，获得批准后创建一份 Issue”。后一个表述让运行时知道什么时候只能输出分析，什么时候可以准备草稿，什么条件下仍不能提交。

状态保存已经发生的事实。它可以包含任务阶段、证据列表、工具调用记录、草稿、审批结果和预算消耗。聊天消息只是状态的一部分。把一切都存在消息历史里，程序就要反复让模型从自然语言推断“用户是否批准过”“哪个结果已经提交”，很容易在长对话中出错。

状态和记忆也要分开。状态服务于当前任务，任务结束后可以归档；长期记忆跨任务保存用户偏好、项目约定或已经确认的事实。把所有历史对话都叫作“记忆”，会让过期资料反复进入新任务。长期记忆需要来源、更新时间和适用范围，也要允许用户查看、更正和删除。像“这个仓库默认使用中文 Issue”可以成为项目偏好，“用户在上次任务里批准了草稿”则只能留在那次任务状态中，不能成为未来写操作的授权。

写入长期记忆本身也是一个有副作用的动作。模型可以提出候选记忆，程序应按规则过滤敏感数据和临时信息，再由用户确认高影响内容。读取时按当前项目和任务召回相关条目，不把整份记忆库追加到每轮上下文。这样既减少上下文噪声，也避免旧任务里的权限和结论污染当前执行。

上下文是某一轮交给模型的信息。它由状态派生，却不必等于完整状态。提交 Issue 之前，模型需要最终草稿、目标仓库和批准记录，不需要再次看到最初搜索返回的全部代码。检索阶段需要查询目标和已有证据，可能不需要长期对话里的寒暄。上下文管理是在每一轮选择有效信息，不是写一条很长的系统提示后保持不变。

运行时还要提供明确终止条件。正常完成只是其中一种：达到最大轮数、超过时间或费用预算、连续调用同一工具没有进展、关键工具不可用、权限不足，都应进入可识别的停止状态。模型可以建议“任务完成”，最终状态仍由代码依据完成条件判断。

长任务需要检查点。每次产生重要状态变化后，运行时把状态持久化。进程重启或人工审批等待几小时，任务可以从最近检查点恢复，不必重新搜索并消耗模型调用。LangGraph 的持久化与 interrupt 机制，以及其他 Agent 运行时的 session 或 resumable state，本质上都在解决这类生命周期问题。[LangGraph 文档](https://docs.langchain.com/oss/python/langgraph/overview)把 durable execution、human-in-the-loop 和持久化列为长时状态任务的核心能力。

恢复会带来副作用重复的问题。假设远端已经创建 Issue，但程序在保存结果前崩溃；恢复后再次调用提交接口，项目里会出现两份任务。提交工具需要幂等键，或在重试前查询既有操作。幂等键应绑定任务与批准版本，草稿被修改并重新批准后才能产生新的提交身份。

模型不负责执行确定性规则。最大轮数、可访问目录、审批是否存在、预算是否耗尽，都由代码判断。把这些规则交给模型节省不了多少代码，却会把稳定约束变成概率行为。

## 研发知识 Agent 的完整分层

把前面的部件放在一起，可以得到一套框架无关的结构：

```text
用户界面 / API
       ↓
Agent 运行时与任务状态
   ↙       ↓        ↘
RAG      工具网关    模型
   ↘       ↓        ↙
检查点、日志、Trace、评测
```

输入层接收用户目标、会话标识、目标项目和身份信息。身份不能只作为一段文字传给模型，它要进入检索过滤和工具授权。接口还要区分新任务、继续任务与审批回复，避免一条“可以”被错误关联到别的草稿。

编排层维护循环和状态转换。它决定当前处于资料收集、分析、等待批准、提交还是结束阶段，控制最大轮数、超时和并发。模型返回工具调用后，编排层不会直接执行，而是交给工具网关做校验和授权。

模型层处理语言理解、查询改写、证据归纳、工具选择和结果表达。不同步骤可以使用不同模型，但这是一项成本与质量选择，不必为了体现架构而拆分。模型配置、提示版本和结构化输出 schema 需要进入 Trace，出现回归时才能还原当时条件。

RAG 层维护相对稳定的项目资料，包括设计文档、维护规范和历史决策。代码搜索、最新 Issue 与构建状态通过实时工具读取。索引中的每个片段带有来源、版本和权限元数据，生成回答时继续保留这些引用关系。

工具网关集中处理工具注册、参数校验、身份授权、调用超时、错误规范化和审计。它还区分只读与写入工具。写入工具默认进入审批流程，具体规则可按风险分级，不能依赖模型自行判断某次操作是否“足够安全”。

状态层保存任务快照和外部操作标识。证据不是一段混合文本，而是一组带来源 ID 的记录；草稿有版本号；批准记录指向确定版本；工具调用带调用 ID 和幂等键。结构化字段让程序能够判断流程，消息历史则保留给模型理解用户表达。

安全层横跨每一层。输入要处理提示词注入和敏感信息，检索要先过滤权限，工具要限制参数与作用域，输出要检查是否泄露无权资料。人工确认属于执行协议，不是一句界面提醒。系统暂停后，必须收到与当前任务和草稿版本匹配的批准，才能继续写入操作。

可观测层记录一次任务经过了哪些模型调用、检索、工具和状态转换。OpenAI Agents SDK 的 tracing 会为模型生成、工具调用、handoff 和 guardrail 等事件记录 span，也允许关闭敏感数据采集。[官方 tracing 文档](https://openai.github.io/openai-agents-python/tracing/)同时提醒了一个容易忽略的边界：调试信息本身也可能包含用户输入和工具结果，生产环境要明确保留策略与访问权限。

一条完整轨迹可以这样运行。用户报告筛选状态刷新后丢失，输入层创建任务并绑定项目权限。模型先调用文档检索，找到项目要求筛选条件可分享；随后搜索代码，发现列表只把分类存在组件 state 中。模型形成带引用的判断，并调用草稿工具生成 Issue。运行时保存草稿后转入 `waiting_for_approval`。用户修改标题并批准，系统生成新版本的幂等键，提交工具创建 Issue，返回远端编号。编排层保存结果，任务才进入 `completed`。

这条轨迹里，任何一步失败都有确定去处。文档没命中时可以继续搜索代码并标记证据不足；代码工具超时可以按策略重试；用户无提交权限时仍可返回草稿；等待批准期间进程可以退出；远端接口限流时任务保留在可恢复状态。模型决定如何继续调查，系统决定哪些行动允许发生。

## 工作流、单 Agent 和多 Agent 的选择

固定步骤已知时，普通程序或工作流通常更合适。上传文件、解析格式、调用三个固定评分器、汇总结果，这些路径可以直接用代码表达。让模型每次重新决定执行顺序，会增加费用和不确定性，又没有获得新的适应能力。

问题求解路径依赖中间结果时，Agent 才开始有实际作用。研发助手无法提前知道要搜索哪几个符号，第一次搜索为空后可能改写查询，发现文档与代码矛盾时还要继续核对历史记录。模型在有限工具集内选择下一步，比穷举所有分支更省开发成本。

单 Agent 能维护清楚的状态和工具权限，就先保持单 Agent。多 Agent 会增加路由、上下文传递、错误归属和评测组合。把“检索”“分析”“写作”分别命名成 Agent，不会自动提高质量，它们也可以是一个 Agent 的不同步骤或普通函数。

职责、权限和失败边界确实不同时，拆分才容易带来收益。比如面向用户的协调 Agent 只能读取资料和准备草稿，提交 Agent 拥有受限写权限，并且只接受带批准凭证的结构化请求。此时分离强化了权限边界，不只是换了几个提示词。

常见编排有两种。主管模式让一个 Agent 保留用户对话和最终答案，把资料检索或代码分析作为专业 Agent 工具调用；handoff 则把当前对话控制权交给专业 Agent。OpenAI Agents SDK 的[编排文档](https://openai.github.io/openai-agents-python/multi_agent/)也区分 agents as tools 与 handoffs：需要统一汇总和控制时适合前者，需要专家直接接管当前回合时适合后者。

还有一条更稳定的边界：代码可以决定的步骤继续由代码编排，只把无法预先写死的选择交给模型。一个系统可以在外层使用确定工作流，某个节点内部再运行 Agent；也可以由主管 Agent 调用一段确定性流水线。工作流和 Agent 不是互斥技术。

## 能跑通的 Agent 仍可能不可靠

Agent 的错误会沿循环积累。第一轮用错查询，第二轮基于错误结果形成判断，第三轮再选择不相关工具，最后仍能生成一段语气完整的结论。只看最终文本，很难知道问题起点在哪里。

上下文膨胀是长任务最常见的压力。每次工具输出都原样追加，几十轮后重要证据被日志和重复摘要包围。处理方式包括给原始结果设置保留策略，把稳定事实写进结构化状态，对旧观察生成可追溯摘要，并在需要时通过来源 ID 重新读取原文。摘要不能覆盖原始证据，否则压缩错误会变成新的事实。

工具参数通过 schema，不代表调用意图正确。模型可能在错误仓库搜索，也可能把用户的讨论当成提交批准。运行时要把目标资源绑定到任务状态，审批动作绑定到草稿版本。关键参数由受信状态提供，不允许模型从对话里自由生成。

重试也会制造事故。读取型请求通常可以安全重试，写入型请求必须考虑幂等与结果查询。模型连续得到相同错误时，运行时应限制重试次数，并把任务转入等待或失败状态。不能指望模型每次都主动停下。

RAG 资料可能过期。索引需要保存文档版本与更新时间，删除或改权的内容要及时从可检索范围移除。回答涉及当前配置、发布状态和实时数据时，应优先调用实时工具。引用存在也不代表引用正确，系统还要检查答案中的具体结论是否能被对应片段支持。

多 Agent 会让未经验证的结论继续传播。专业 Agent 的输出应该带证据和结构化状态，主管不能只收到一段无法追溯的自然语言总结。高风险链路可以增加独立校验，但校验 Agent 同样是概率模型，不能替代权限规则和确定性验证。

Trace 解决定位问题，也引入数据面。模型输入可能包含私有代码，工具结果可能包含令牌、邮件或用户资料。日志系统需要脱敏、权限、保留期限和删除机制。调试方便不能自动优先于数据承诺。

预算和停止策略也属于可靠性。为每个任务设置最大模型轮数、工具调用数、总时间和费用上限，连续无进展时提前停止。停止后返回已经确认的证据、尚未完成的部分和下一步所需条件，比编造一个完整答案更有用。

## Agent 评测要检查整条轨迹

传统问答评测常把输入与最终答案放在一起比较。Agent 多了工具、状态和环境变化，只看最后一句会漏掉很多问题：答案碰巧正确，但调用了无权工具；任务确实完成，却重复创建两份 Issue；Agent 得到充分证据后仍进行了十次无效搜索。

确定性逻辑先做单元测试。工具 schema 是否拒绝多余字段，权限策略是否阻止越权仓库，状态机能否从 `waiting_for_approval` 恢复，幂等键能否挡住重复提交，这些测试不需要调用真实模型。OpenAI Agents SDK 当前也提供面向编排行为的确定性测试工具，可用脚本模型验证工具调用、handoff、guardrail、重试和 session 行为，而不发送真实模型请求。[官方测试文档](https://openai.github.io/openai-agents-python/testing/)反映的是同一原则：程序拥有的行为应尽量用普通测试锁住。

固定任务集用于比较 Agent 的端到端表现。每条样本除了用户输入，还要准备允许访问的资料、工具环境、预期结果和禁止动作。研发知识助手的样本可以覆盖正常定位问题、文档与代码矛盾、搜索无结果、工具超时、用户拒绝草稿、重复审批和权限不足。

指标要对应失败位置。任务成功率看最终目标；工具选择与参数准确率看行动；证据召回率和引用支持度看 RAG；平均步骤数、延迟和费用看效率；越权调用数、未经批准的写操作数看安全。一个总分无法说明应该改检索、提示、工具还是状态机。

轨迹评测还要允许多条正确路径。同一个问题可以先查文档再搜代码，也可以从代码符号切入，只要证据充分、步骤合理且没有违反约束。评分器可以检查关键事件和最终环境状态，不必要求工具调用序列逐项相等。

模型或提示更新后，用同一批任务做回归。通过数量变化只是入口，还要查看旧失败是否修好、新失败从哪里出现。真实模型评测存在波动，可以重复运行重要样本并记录模型版本、参数、提示版本、工具版本和知识库快照。否则两次结果无法解释。

线上监控与离线评测各管一段。离线任务集适合在发布前发现回归，线上数据能暴露没有覆盖的新输入和真实工具故障。线上失败经过脱敏和去重后可以补进评测集，但涉及私有代码与用户数据时，采集范围必须符合产品承诺。

研发知识助手是否可靠，最后看的是一组可观察结果：它能找到相关证据，证据支持判断，工具调用符合权限，失败后能够停下或恢复，提交动作确实经过当前用户对当前草稿的批准。模型提供理解与选择能力，运行时把这些选择限制在可验证、可恢复的执行过程里。
