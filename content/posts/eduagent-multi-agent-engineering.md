教培场景里的 AI 需求很难塞进一次模型调用。学员答疑要查私有资料，试卷批改要按题型处理并让老师确认，简历审查要并行评估多个维度，模拟面试还要记住阶段和上下文。四类任务都依赖模型，却有完全不同的控制流和失败边界。

讲义中的 EduAgent 把它们拆成四个专业 Agent，再用统一入口和编排器接起来。这个设计值得看的是执行方式：每类业务都有适合自己的控制流，模型、记忆、重试和认证则收进公共层。

## 先把系统分成三层

EduAgent 的整体结构可以收成三层：地基层、Agent 层和集成层。

地基层提供配置、日志、异常、重试、模型工厂、认证、记忆、知识库和本地模型。它不判断简历该怎么评分，也不关心面试到了哪个阶段，只负责给上层稳定的通用能力。

Agent 层承载业务流程。每个 Agent 是一张独立的 LangGraph 图，有自己的 State、节点和边。简历审查、智能问答、试卷批改和模拟面试可以分别开发和验证，某一张图发生变化时，不必改动其他业务流程。

集成层把这些图放到一个入口后面。统一接口先识别用户意图，再把明确的任务交给编排器。需要组合任务时，编排器按顺序执行多张图，并把前一步的结构化输出放进下一步的上下文。

这三层的边界让依赖方向保持简单：Agent 复用地基，集成层调用 Agent。业务判断不会散进公共工具，编排代码里也不需要重写任何一张图的内部步骤。

## 四个 Agent 对应四种控制流

简历审查适合固定流水线。PDF 文本经过结构化抽取后，六个评分维度可以并行执行，等所有结果返回再聚合问题和总评。这里的重点是 fan-out 和 fan-in，一份输入被拆成互不依赖的评估任务，最终再合成一份报告。上传接口先返回任务 ID，耗时较长的审查留在后台运行，也避免 HTTP 请求一直占着连接。

智能问答面对的是另一类问题。它要先判断问题类型，再决定直接回答、改写查询、检索知识库或联网兜底。检索之后还要根据重排结果和置信度选择生成路径，多轮对话则通过检查点保留记忆。条件边和状态决定了这张图的复杂度，单看节点数量很难判断。

试卷批改把确定性逻辑、模型判断和人工确认放在同一条流程里。客观题走规则比对，简答题和代码题分别交给模型评估，三路并行后汇总。图在发布成绩前通过 `interrupt()` 暂停，教师提交决定后再用 `Command(resume=...)` 恢复。对有真实后果的结果，人工确认点是业务流程的一部分，不能只靠提示词表达“请谨慎”。

模拟面试需要显式状态机。热身、技术基础、项目深挖和收尾各有自己的推进条件，当前阶段由代码字段记录，LLM 只生成当前阶段需要的内容。这样一来，轮数上限、追问门槛和强制结束都能由确定性逻辑控制，不必让模型反复阅读全部历史后猜测流程走到了哪里。

四张图没有追求统一形状。固定任务走直线，并行评估用聚合，知识问答用条件路由，关键决策插入人工节点，长流程对话交给状态机。控制流跟着业务约束走，比先决定“做一个 Agent”再往里面塞能力更容易维护。

## 公共地基决定系统能不能长期改

多 Agent 系统很容易在第四个、第五个业务接入时开始重复：每个节点各自创建模型客户端，各写一套重试，各存一种消息格式，错误发生后也没有统一的状态。短期看只是几段重复代码，模型配置或降级策略一变，差异会迅速扩散。

EduAgent 把取模型收进统一工厂，把异常和重试放进公共模块，把多轮状态交给 `MemorySaver` 和 `thread_id`。Agent 节点只描述输入、动作和需要更新的 State 字段。模型替换、缓存策略或重试规则发生变化时，公共入口可以集中处理。

容错也需要按失败影响来设计。讲义中的试卷批改三轨使用 `asyncio.gather(return_exceptions=True)`，其中一路失败不会抹掉另外两路结果，缺失部分留给教师补充。统一入口的意图路由失败时则降级到普通问答，让请求仍有一条可用路径。两种降级处理不同，因为前者涉及成绩完整性，后者只是在路由不确定时选择较宽的入口。

公共地基还给可观测性留下了统一位置。模型调用、重试、异常分类和任务状态都从固定入口经过，日志才能回答“哪张图的哪个节点失败了”“重试是否生效”“最终走了哪条降级路径”。没有这些信息，流程图画得再完整，线上问题也只能靠猜。

## 编排层只做路由和串联

EduAgent 把统一入口和编排器拆成两个角色。统一入口处理用户表达，包括规则前置拦截、意图分类和 SSE 事件分发；编排器接收已经明确的 Agent 类型，负责调用对应图或执行预置 Pipeline。

这个边界能限制编排层继续膨胀。简历如何评分属于简历图，面试何时进入项目阶段属于面试图，知识库置信度不足时怎么回答属于问答图。编排器只需要知道这些图的输入和输出契约。

多 Agent 串联依赖结构化数据。讲义里给出的求职流程先做简历审查，再把审查结果作为模拟面试的背景。前一步如果只返回一段自由文本，后一步只能重新解析和猜测。稳定的字段让上下文注入、失败定位和结果聚合都有明确边界。

交互层的计划与后端的一次性 Pipeline 也可以分开。用户可能需要按步骤确认和跳转，程序内部则可能要连续执行多张图。两者共享任务顺序，却不必共享同一种执行方式。

## 什么时候值得拆成多 Agent

业务名称不同，不足以成为拆分理由。两个任务如果共享同一份状态、同一套失败处理和几乎相同的控制流，拆成两张图只会增加路由与数据转换成本。

更适合拆分的信号来自边界：输入输出能形成稳定契约，流程可以独立运行和测试，状态生命周期不同，失败后的责任也不同。简历审查是一次性后台任务，问答依赖检索和会话记忆，试卷批改必须等待教师，模拟面试要跨多轮保持阶段。它们分别满足这些条件，所以独立成图有实际收益。

组合需求则留给编排层。先审简历再模拟面试，是两项完整能力的串联，不需要在简历图里嵌入面试逻辑。新增 Agent 时也可以沿用同一判断：先确定业务控制流，再定义 State 和结果契约，最后接入公共地基与统一入口。

EduAgent 提供的工程启发很具体。多 Agent 设计从职责、状态和失败边界开始，Agent 数量只是这些边界划分后的结果。
